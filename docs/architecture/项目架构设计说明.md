# 项目架构设计说明

> 本项目采用 **Next.js（App Router）** 作为应用框架，前端页面与后端 API 统一在同一代码仓库内组织。业务能力以 `app/(app)`（页面）与 `app/api`（接口）为边界，通用能力沉淀在 `app/lib`。

---

## 2. 分层与职责约定

### 2.1 UI 层：`app/(app) + app/components + app/hooks`

* `app/(app)`：页面路由与页面级数据组织（列表、详情、表单、交互编排）
* `app/components`：可复用 UI 组件（输入框、导航、弹窗、卡片、列表项等）
* `app/hooks`：可复用交互逻辑（节流、防抖、快捷键、滚动控制等）

约定：

* 页面层不直接写 SQL/DB 逻辑；
* 对外数据交互统一通过 `app/api/**`。

---

### 2.2 API 层：`app/api/**/route.ts`

* 对外提供 HTTP 接口（CRUD、搜索、AI 对话等）
* 负责：

  * 请求参数解析
  * 请求体校验
  * 调用 `app/lib/**` 完成数据/业务处理
  * 输出统一返回结构（含错误结构）

约定：

* `route.ts` 中不落复杂业务编排；
* 可复用逻辑沉淀到 `app/lib/**`，避免接口层膨胀。

---

### 2.3 通用能力：`app/lib/**`（保持不变的核心）

> `lib` 的职责与设计原则 **基本不变**：它承载可复用的基础设施能力、类型、协议、校验、数据库访问、工具封装等，供 API 层与页面层调用。

---

## 3. 公共模块（`app/lib/**`）

> 以下是你原先“公共模块”能力的**现行路径映射**与用途说明（功能不变，主要是目录对齐）。

| 模块              | 现行位置                                        | 用途                                                                                                      |
| --------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `db/`           | `app/lib/db/` + `app/lib/db.ts`             | PostgreSQL 连接与 drizzle 封装；schema 与迁移配合 `drizzle/`                                                       |
| `repositories/` | （可选扩展位）`app/lib/repositories/`              | DAL：表/实体级 CRUD、查询组合；不写业务编排                                                                              |
| `file-storage/` | （可选扩展位）`app/lib/file-storage/`              | `FileStorage` 统一接口（upload/download/delete/exists/metadata/sourceUrl/downloadUrl/createUploadUrl）+ 多后端驱动 |
| `validations/`  | （可选扩展位）`app/lib/validations/` 或就近文件内 schema | zod：请求体/配置/工具参数校验；统一校验入口                                                                                |
| `env/`          | （可选扩展位）`app/lib/env/`                       | 环境变量读取 + zod 校验（DB/Auth/Storage 等）                                                                      |
| `logger.ts`     | （可选扩展位）`app/lib/logger.ts`                  | 结构化日志能力（服务层/中间件复用）                                                                                      |
| `errors.ts`     | （可选扩展位）`app/lib/errors.ts`                  | 统一错误类型/错误码，供 API 返回一致结构                                                                                 |
| `const.ts`      | （可选扩展位）`app/lib/const.ts`                   | 常量、枚举、约定字段                                                                                              |
| `utils.ts`      | `app/lib/format.ts` / `app/lib/id.ts` 等     | 字符串/类型/格式化等通用工具                                                                                         |

说明：

* 当前项目中，`db.ts / db/schema.ts / query.ts / queries.ts / types.ts` 已覆盖绝大多数基础设施与领域类型能力；
* `repositories/file-storage/env/logger/errors/const/utils` 等模块如果未来需要增强，可按上表落位到 `app/lib/` 中，不影响现有代码组织。

## 4. 核心业务模块

> 以当前项目实际代码为准，业务域主要围绕 Customers / Todos / Conversations / AI Assistant 展开。

| 业务域           | 页面                          | API                             | lib 支撑                                                  |
| ------------- | --------------------------- | ------------------------------- | ------------------------------------------------------- |
| Customers     | `app/(app)/customers/**`    | `app/api/customers/**`          | `app/lib/types.ts`、`app/lib/db.ts`、`app/lib/queries.ts` |
| Todos         | `app/(app)/todo/**`         | `app/api/todos/**`              | `app/lib/types.ts`、`app/lib/db.ts`                      |
| Conversations | （在 AI 页或客户页关联）              | `app/api/conversations/**`      | `app/lib/db.ts`、`app/lib/types.ts`                      |
| AI Assistant  | `app/(app)/ai-assistant/**` | `app/api/claude-agent/route.ts` | `app/lib/chat-schema.ts`、`app/lib/claude-agent-kit/**`  |

## 5. AI 对话交互协议（统一入口）

### 5.1 协议与校验

* `app/lib/chat-schema.ts`：统一前后端对话请求体/消息结构/附件结构（zod + 类型）
* `app/components/AIInputDock.tsx`：负责把 UI 输入整理为协议结构并发起请求
* `app/api/claude-agent/route.ts`：服务端接入入口（校验请求体 → 调用 agent → 流式返回）

约定：

* **对话请求体只允许使用 `chat-schema.ts` 定义字段**；
* UI 组件如需扩展 part 类型，必须先在 schema 中落地。

---

## 6. 数据库与迁移

* `docker-compose.yml`：本地 Postgres
* `app/lib/db/schema.ts`：表结构定义
* `drizzle.config.ts`：迁移配置
* `drizzle/`：迁移产物目录

约定：

* schema 的变更必须通过 drizzle 的迁移流程进入版本控制；
* API 层不直接写原生 SQL，统一走 drizzle + lib 查询封装。

---

## 7. 测试目录与规范

* 单元测试（可选）：围绕 `app/lib/**` 的纯函数、schema 校验、查询组合
* 集成测试（可选）：`app/api/backend.integration.test.ts`
* E2E：`tests/e2e/*.spec.ts`（覆盖关键用户路径）

约定：

* lib 的逻辑优先可测试；
* 接口层测试关注：输入校验、状态码、返回结构、数据库写入效果。

---

## 8. 技术栈

* Next.js（App Router）+ React
* PostgreSQL + drizzle-orm + drizzle-kit
* zod（协议/请求体校验）
* AI：`ai` / `@ai-sdk/react` + Claude Agent SDK（项目内封装于 `app/lib/claude-agent-kit/`）
* 测试：Vitest + Playwright
* 部署/本地依赖：docker-compose（Postgres）
