# Independent task result handoff: Admin contract

## 当前状态

Dream 当前使用父轮次内的 `wait_threads` 等待目标 Thread 完成，并把目标 final 直接返回正在运行的父轮次。Dream 不启动后台 `TaskResultCoordinator`，不提供公开 `task-results` 路由，也不依赖来源 Thread 技术消息或结果卡片完成交付。Registry199–204、migration 0068 与 `task-return:dispatch` 保留为 Admin 侧兼容能力；当前 Dream 发布路径不调用这些操作，也不应仅为 `wait_threads` 启用该 service scope。

本稿定义保留能力的数据库与授权边界，供既有数据识别和后续显式兼容评审使用。它不代表当前 Dream 产品需要部署后台回传 worker。

## 背景与问题

`chat_task_session` previously recorded task creation and first launch only. Migration 0068 was designed to retain a completed target assistant turn after the source Thread ended and to provide source authority independent of the browser OAuth token used at task creation. Dream subsequently selected in-turn `wait_threads`; therefore this persistence path is retained as an Admin compatibility boundary rather than the active completion mechanism.

## 目标与边界

Forward migration `0068_cool_psylocke` publishes `dream.chat-task-result.v1` after adding `chat_task_result`, immutable return intent on `chat_task_session`, and claim-bound source Runtime delegation columns. Admin owns result identity, final-message validation, revision transitions, authorization, encrypted delegation recovery and audit. A consumer of this compatibility capability would own source Thread admission, single consumer, SDK resume, Gateway Runtime and event delivery. Current Dream does not instantiate that consumer. No normal business database is migrated by startup or by this worktree's validation.

Service tokens can carry `task-return:dispatch` only when the exact confidential client in Admin `DREAM_DATA_SERVICE_CLIENTS` includes that background scope. The OAuth catalog derives its `client_credentials` scopes from that registration; Admin then intersects verified token scopes with the configured scopes on each request. Existing installed environments are preserved by `setup-env.mjs` and do not acquire the new scope automatically. Current Dream `wait_threads` does not require this scope. Any future compatibility rollout requires a separate review of the consumer, target capability, service registration and token provisioning. Missing registration, token scope or capability fails closed; no production configuration or normal database is changed by this worktree.

Existing `task-session.create` keeps `return_result=false`, so ordinary navigation tasks do not wake the source Agent. `task-session.create-returning` has the same closed input and atomically sets `return_result=true`; replay with the other create mode conflicts. The model cannot supply an actor, Claude session, process owner, result body or target completion status.

The Admin application can run while its database is still at 0067. `ChatThreadRepository` checks the exact result capability before task creation: without it, the ordinary `task-session.create` uses an explicit pre-0068 Drizzle column projection and never selects, inserts or returns the absent `return_result` column. `task-session.create-returning` fails with `DREAM_DATA_SCHEMA_NOT_READY` before creating a target Thread. With 0068 published, both creation modes use the full table mapping and freeze the return intent. This preserves existing task operations during an expand-first rollout; the pre-0068 mapping is an application projection, not a second schema migration.

## 概念与规则

| Entity | Stable identity | Rule |
| --- | --- | --- |
| Target final | Target Thread, `target_turn_id`, final assistant message | Admin requires `turnStatus=completed`, `history_projection_version=1`, nonempty final text and the canonical final part. |
| Notification | `task_id + target_turn_id` | Unique row and stable notification ID. The source and target Thread must still belong to the task actor. |
| Source claim | Notification ID, revision, claim ID, source turn ID | At most one dispatching result per source Thread. Queued, selected, dispatching or uncertain `chat_input_queue` records block a new claim. |
| Source technical input | Server-generated message ID | The compatibility flow writes one source `chat_message(role=user)` with `metadata.kind=task-session-result`, notification, task, target turn, claim and source turn references. Current Dream does not consume or render this path. |
| Source authority | Notification and claim bound | Admin returns a renewable `server-persistence` grant and a separate `gateway-cli` grant for the source Thread. Both resolve only while the same notification remains `dispatching` with that claim. |

The technical source input exists for a compatibility consumer that resumes the source through a persisted input message. Its metadata identifies a service event; it is not a user-authored chat turn. Such a consumer must pass the server-generated ID through the existing pre-persisted input path and keep the ordinary queue and Thread consumer ordering. The claim response includes the Admin-derived canonical actor ID, source Thread's saved Claude session ID and exact input text; none of these is accepted as an input override.
The input text uses the task title and final result in readable Chinese and keeps task, turn and claim identifiers in metadata. Admin checks its encoded size against the configured `DREAM_DATA_MAX_BODY_BYTES` limit before claiming; an oversized result remains pending with `TASK_SESSION_RETURN_INPUT_TOO_LARGE`.

### Operations

| Operation | Authority | Input | Result |
| --- | --- | --- | --- |
| `task-session.result-commit` | Current target Thread user OAuth or live target `server-persistence` grant | `target_thread_id`, `target_turn_id`, `target_final_message_id` | Existing or new notification; `null` for a nonreturning or ordinary Thread. |
| `task-session.result-list` | Current source Thread owner or exact source grant | `source_thread_id` | Durable cards including target final text and delivery state. |
| `task-session.result-claim` | Confidential Dream service with `task-return:dispatch`; no user bearer | `notification_id`, `expected_revision`, server-generated `source_turn_id` | Dispatching notice, source technical input, source session, actor ID and both bounded grants. |
| `task-session.result-claim-next` | Same confidential service | Empty object | Atomically claims the earliest eligible pending result, or returns `claim=null`; Admin generates the source turn ID. |
| `task-session.result-settle` | Same confidential service | Notification ID, expected revision, claim ID and `delivered`, `failed` or `mark_unknown` action | Terminal notification. For `delivered`, Admin derives the unique source final assistant message ID from the claimed source turn and notification metadata. |

When the physical capability is present, `chat-message.persist` inserts the notification **in the same transaction** as a new completed target assistant message. `result-commit` is an explicit idempotent reconciliation operation for an already saved final message **only when its task has `return_result=true`**. It may reconcile a returning task whose final message was saved before result insertion, but it does not backfill pre-0068 tasks: migration 0068 gives existing task rows `return_result=false`, and the repository returns `null` for them. A compatibility consumer must use the current renewable target Thread grant for that call; an expired creation-time browser token is not a background authority.

The claim transaction also creates both Runtime grants and their encrypted recovery rows. Repeating the exact claim input after an uncertain HTTP response recovers the same input and grants while they are live. The bearer values are never stored in `dream.operation_receipts`, audit metadata or logs. Claim identity and encrypted grant rows serve as its durable receipt. Other writes use the normal operation receipt and audit transaction.

For `result-claim-next`, a compatibility consumer must recover an uncertain HTTP response by calling **the same operation with the same `request_id` and empty input**. A nonempty claim has no generic `/receipts/{request_id}` entry because such an entry would store both bearer values in plaintext; an absent generic receipt is not evidence that the claim failed. The same request ID is bound to the original claim and cannot select a different task. After that claim is terminal, the retry returns `TASK_SESSION_RETURN_STATE_UNKNOWN`. The token-free empty response alone uses the ordinary receipt endpoint.

After a compatibility consumer restarts, `result-claim-next` first reconciles `dispatching` notices. It leaves a claim in `dispatching` while **any** source grant remains active: the source result final may have committed while the same owner still drains queued user input. Once every grant has expired, been revoked or disappeared, an exact unique committed source final becomes `delivered`; without that final the notice becomes `state_unknown`. An active consumer may instead call `result-settle(delivered)` after the whole owner exits. This scan never resends source input. Both `result-claim-next` and owner-scoped `result-list` also upgrade a `state_unknown` notice to `delivered` when exactly one late source final is committed with the claimed source turn and notification ID. Otherwise uncertainty remains terminal and is never retried automatically. The service then discovers pending notifications without a user token or known source Thread ID. It walks pending rows in creation order with PostgreSQL `SKIP LOCKED`, skips sources blocked by unresolved input or another dispatch, and leaves those notices pending. It skips actors whose canonical subject is no longer active. A consumer may call this only when its current topology can establish source Thread ownership and admission; the Admin operation does not route work between processes. Its service/request digest is unique on the claimed result; repeating the same request recovers that result and both encrypted grants. An empty scan writes a token-free operation receipt so an exact retry remains empty even if another task becomes pending. After a claimed result turns terminal, the old request reports uncertainty rather than claiming another result.

### Compatibility source continuation sequence

This sequence is inactive in the current Dream release. It applies only if a future consumer is explicitly enabled after product and deployment review.

1. The consumer's Thread owner and admission path select a pending notice. The Admin claim additionally refuses unresolved durable user input and a second active result claim.
2. The consumer resumes the source Claude session using the returned source session ID and the returned technical input ID/text. Persistence calls use the returned source `server-persistence` grant; Gateway Runtime uses the returned `gateway-cli` grant.
3. The consumer persists the source final assistant message with `turnId=source_turn_id`, `turnStatus=completed`, final-only projection and `taskResultNotificationId=notification_id` in metadata. After SDK consumption and message persistence both succeed, it calls `result-settle(delivered)`.
4. A failure proven to occur before SDK submission may use `failed` and `TASK_SESSION_RETURN_NOT_SUBMITTED`. If submission, process ownership or receipt is uncertain, the consumer calls `mark_unknown` and must not automatically resubmit that notification.

No source worker or browser may infer delivery from target text, HTTP success alone or a displayed card. A compatibility consumer must keep `pending` if owner/admission or a required capability is unavailable. If an owner is lost after claiming, the notification remains `dispatching` until the consumer explicitly reconciles it to `state_unknown`; this capability does not add cross-process owner routing or a second scheduler.

### Migration and validation

Migration 0068 is additive for existing tasks (`return_result=false` by default) and does not copy historical business content. The `runtime_delegations` source-shape CHECK is replaced in one migration transaction; its brief table lock and validation scan require review before an operator applies it to a persistent database. The new task-result partial unique index protects source dispatch concurrency. If migration fails, PostgreSQL rolls the transaction back; an applied migration is repaired only by another forward migration. Old delegation resolution selects its pre-0068 columns until the exact capability is present, so application compatibility does not require immediate 0068 activation.

The isolated `run-chat-input-queue-contract.mjs` runner replays the journal into a named disposable embedded PostgreSQL database, verifies the capability, constraints and ACL plan, then executes the production Chat and result repositories. It proves atomic target completion, owner denial, claim replay, source input creation, persistence and Gateway grants, terminal settlement and grant fencing. These are technical checks, not normal-account or real-model acceptance.

The runner first applies the immutable journal through 0067, calls `probe-task-session-pre-result.ts` against the production Chat operation service and confirms legacy create/replay/get/launch/target-final plus returning-task capability denial. It then applies 0068 forward in the same disposable database and runs the Admin domain and HTTP Route Handler result probes. This checks application compatibility across the release boundary; it does not activate 0068 in `ink-memory`.

The same runner invokes `probe-task-result-route.ts` after its domain probe. That check uses a temporary signing key and synthetic confidential client registered only in the disposable database/process. It calls the production Admin Route Handler and verifier with strict request DTOs: missing service token is rejected, a token lacking `task-return:dispatch` is rejected, an authorized claim and exact replay return the same claim authority, the source `server-persistence` grant reads only its own Workflow context, settlement requires a committed source final, and the terminal claim cannot be replayed into another dispatch. `workflow-context.resolve` checks the exact Thread and grant purpose while keeping Workflow activation under its own operation. It exercises the API ingress without modifying the normal Admin/Dream/Gateway processes.

`deck-chat-context.resolve` keeps its Registry105 request/response DTO and capability hash. For a source result, the Handler resolves only an active `server-persistence` grant for the calling service with `dream:read`, null Run and editor scope. The Repository locks the grant's owner Thread and checks that its `deck_id` and `voice_id` exactly match the submitted selection before reading the owner Deck and selected Voice. A missing or mismatched binding fails before Dream submits to the SDK; OAuth Deck reads continue through their original actor ownership path. This fixes a previously missing capability for Deck-bound source Threads without adding a schema migration or weakening the task-result claim fence.

A compatibility consumer's initial source result turn may be followed by queued user input inside the same owner, using the same claim grants. The consumer must distinguish initial-turn completion from whole-owner completion and wait for the owner to release its Thread lock before `result-settle(delivered)` revokes the grants. A later queued user turn failing does not erase the already committed result final; an uncertain initial result or lost owner keeps the notification out of `delivered` until Admin verifies its exact final message.

`result-claim-next` runs concurrently with source execution. Its recovery scan must preserve `dispatching` after the first source final while any claim grant is active; otherwise the next poll would fence the grant before queued input finishes. The isolated production Route Handler probe calls `claim-next` in this interval and checks the original revision and source context grant. The domain probe additionally expires both grants and checks that recovery then verifies the exact final before marking `delivered`.

Run `node scripts/check-chat-task-result-readiness.mjs` with `DREAM_DATA_DATABASE_URL` set to the current Dream data-role DSN, `EXPECTED_DATABASE_NAME` set to the exact database name, `INK_ADMIN_DREAM_SERVICE_CLIENT_ID` set to the Dream confidential client ID, and `DREAM_DATA_SERVICE_CLIENTS` set to the current Admin registration. It opens a read-only transaction and reports `ready` only if the 0068 capability hash, structural fields, single-dispatch index, current data-role DML grants and that client's `task-return:dispatch` registration all match. Exit 2 with named missing gates means the completion handoff must remain disabled. This check does not establish that an OAuth token was reprovisioned or that the live Dream process has loaded the new code; verify those separately before real-business acceptance.

Run `node scripts/run-chat-input-queue-contract.mjs` from the Admin repository root for the isolated Admin contract. Its final JSON `handoff_receipt` exposes the fixture task, target final, notification, claim, source input, source final and revision IDs without bearer values. The runner owns and removes only its named `ink_chat_input_queue_test_*` PostgreSQL database and calls production operation services inside real transactions. It does not invoke a Dream background coordinator; current Dream completion is verified in the Dream repository through `wait_threads` tests.

The HTTP operation sequence is: `task-session.create-returning` with the same input as `task-session.create`; `chat-message.persist` for a completed target assistant final; `task-session.result-list` on the source Thread to observe the automatic `pending` notification (or `result-commit` with target Thread, turn and final message IDs to reconcile); service `task-session.result-claim-next` with `{}` to receive `claim.result`, source input/session/actor and two bounded grants; source `chat-message.persist` with the returned source turn ID and `taskResultNotificationId` metadata; then service `task-session.result-settle` with notification ID, the claim's revision and claim ID, and `action=delivered`. An exact retry of `result-claim-next` before settlement returns the same claim and recovered grants. After settlement, the old request fails with `TASK_SESSION_RETURN_STATE_UNKNOWN` and cannot claim a different result; a new request may claim the next eligible notification. Repeating the source input submission is never part of recovery.
